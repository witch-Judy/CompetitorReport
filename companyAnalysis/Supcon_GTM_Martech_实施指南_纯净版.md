# Supcon GTM Martech 具体实施指南（纯净版）

**基于**：Supcon Marketing Technology Recommendations 既定架构与阶段规划  
**目标**：将「产品/行为数据 → 线索/商机」的闭环落地为可执行步骤，明确各阶段数据与技术的使用方式；覆盖生命周期营销（首触→高价值用户、培育、再激活、多区域）与产品营销（定位与叙事、发布 GTM、销售赋能）的设计与协同。

---

## 1. 指南定位与适用范围

**本指南面向团队全体**：需求与架构负责人、网站开发、前端。大家可据此了解各阶段**自己要做什么、队友做什么、共同产出是什么**，以及对齐范围与优先级。

本指南在**不改变**《Supcon Marketing Technology Recommendations》中 Phase 0 → Phase 1 → Phase 2 总体架构的前提下，将 GTM/Martech 职责拆解为：

- **谁在什么阶段做哪些事**（需求设计、验证闭环、统一中台）
- **数据与技术在漏斗各阶段的用途**（Attract → Inform → Convert → Engage）
- **与现有文档的对应关系**（指标体系、数据实体、HubSpot 配置、数据平台需求规格）

**团队角色简述**（便于后文对照）：
- **需求侧**：负责「要什么、验收什么」——需求与架构负责人（产品+数据口径、Phase 0 产出、验收标准）。
- **执行侧**：负责「怎么做、谁做哪块」——**网站开发**（追踪与数据对接、GTM/HubSpot 追踪、事件上报、API 对接）、**前端**（表单与前端体验、HubSpot 表单嵌入、落地页、前端交互与校验）。

**漏斗与数据流**（贯穿 Phase 1 / Phase 2）：

| 漏斗层 | 要回答的问题 | Phase 1 技术 | Phase 2 技术 |
|--------|--------------|-------------|-------------|
| **Attract** | 流量从哪来、内容/活动效果 | GA4 + GTM + HubSpot 追踪；流量报表 | 统一平台：来源/内容维度、归因 |
| **Inform** | 谁留资、谁算 MQL、培育与再激活效果 | Forms + 工作流 + 打分 + 培育/再激活流 | 事件表 + 统一漏斗、A/B 与 persona 分析 |
| **Convert** | Demo/商机进 CRM、转化率、维度分析 | HubSpot CRM + Deal/Pipeline + 报表 | MA + CRM + 行为打通、转化分析 |
| **Engage** | 客户健康度、扩展/流失信号 | Contact 属性 + 列表/标签 | 产品数据入仓 + 健康度/扩展/流失看板 |

### 2.1.1 与「AI-ready GTM 架构图」的对应

若团队已有**「AI-ready Go-To-Market Operating System」架构图**（目标：通过数据、自动化与持续学习，把市场注意力转化为可预测、合格的收入），可按下面方式与本指南的 Phase/Sprint 对齐，使 Sprint 更贴合该架构。

| 架构图组件 | 在本指南中的阶段 | Sprint 对应 | 说明 |
|------------|------------------|-------------|------|
| **Integration Layer**（Connectors + Mapping + Scheduler） | Phase 1 先打通；Phase 2 统一入 Marketing Data Layer | **1.1**：网站 + HubSpot Form + GA（及可选 LinkedIn/YouTube 来源）；**2.2**：HubSpot/GA/CRM/LinkedIn Analytics 等统一入仓 | 流量来源（LinkedIn/YouTube→网站 HubSpot Form→customer+Event）、行为（Website→GA、LinkedIn→LinkedIn Analytics）、既有客户（regionally managed→HubSpot API）在 Phase 1 先以 HubSpot+GA 为主落地；Phase 2 再统一进 Marketing Data Layer。 |
| **Marketing Data Layer**（Data layer + dashboard + apps） | Phase 2 建设 | **2.1–2.2**：数据平台/数仓选型、ETL、事件与维度模型；**2.5**：统一看板 | 核心实体：**Customer (Person, Company)**、**Content (Whitepaper, Blog, Video)**、**Campaign (Webinar, Event, Ads)**；**Event Log**（Who did what, when, via which content & campaign）；衍生：Unified Identity、Content Graph、Conversion Paths、History。Phase 0 需求设计时即可按此实体与 Event Log 结构写《数据实体与事件规范》。 |
| **HubSpot**（Workflows are execution atoms; Nurture Orchestration signal-based） | Phase 1 | **1.1**：追踪+表单→customer+Event；**1.2**：打分+MQL 工作流+**原子工作流**（Email/Content/Campaign 各一条）；**1.3**：**Nurture Orchestration**（培育+再激活编排）、Dashboard 初版 | 「原子工作流」= 单职责工作流（如仅邮件、仅内容、仅活动），由 Nurture Orchestration 按信号组合；Phase 1 可先实现「至少 1 条培育流+1 条再激活流」，编排逻辑可先规则驱动，Phase 2 再引入 Lead Score 等信号。 |
| **Salesforce**（Hot Leads + Scoring System → Feedback） | Phase 1 若有 CRM；Phase 2 打通 | **1.1**：若有 Salesforce，对齐 Hot Leads 来源（HubSpot 分配）与字段；**2.2–2.4**：CRM 入仓、Reverse ETL 回写；销售侧 **Scoring System 的 Feedback** 可反馈回 HubSpot/数据层，用于持续优化打分与培育 | 「谁该找销售、何时、为何」与架构图中 Hot Leads + Feedback 闭环一致；Phase 0 对齐时明确 Hot Lead 标准与 Feedback 口径。 |
| **Dashboard**（Data analysis + Attribution + Nurture Decision Engine, Human+AI） | Phase 1 初版；Phase 2 进阶 | **1.3**：初版 = 流量、线索、管线、客户数等（Query 基于 HubSpot 报表）；**2.5**：统一看板 = 基于 Event Log + Customer/Content/Campaign 的**归因分析**与**培育决策**（Human+AI） | Phase 1 Dashboard 以 HubSpot 内报表为主；Phase 2 统一数据层后，Dashboard 升级为「Query over Event Log + Customer/Content/Campaign」+ 归因 + Nurture Decision Engine（先人为主，AI 按需叠加）。 |
| **Business Card Collection App**（线下名片/名单→Clean Customer Data） | 可选，Phase 1 或 Phase 2 | 若需线下活动数据入统一数据层，可在 **1.1** 或 **2.2** 纳入：定义「名片/名单」字段与清洗规则，输出 Clean Customer Data 写入 HubSpot 或 Marketing Data Layer | 架构图中该 App 输出 Clean Customer Data 进 Marketing Data Layer；若团队有线下活动需求，可在 Phase 0 需求中列入「可选数据源：线下名片/名单」，Sprint 1.1 或 2.2 排期。 |

**对 Phase 0 的细化建议（贴合架构图）**

- **数据实体**：在《数据实体与事件规范》中显式采用架构图里的 **Customer (Person, Company)**、**Content (Whitepaper, Blog, Video)**、**Campaign (Webinar, Event, Ads)**，以及 **Event Log** 的「谁、在何时、做了什么、通过哪条内容、哪场活动」结构；与文档 9.4 的 Contact/Company/Deal 及事件表对应即可。
- **必选事件**：与架构图一致——表单提交（Demo/下载/Webinar）、内容互动（Whitepaper/Blog/Video）、活动（Webinar, Event, Ads）均记为 Event Log 的一条；Phase 0 第 2 周确定「必选事件」时可直接按 Content + Campaign 维度列清单。
- **Integration Layer 范围**：Phase 0 可明确 Phase 1 先接哪些源——例如**网站 + HubSpot Form + GA** 必选，**LinkedIn 流量/行为、YouTube、区域客户数据**按需列入 Phase 1 或 Phase 2；与架构图左侧 Traffic Sources / Existing Customer Data 一一对应。

**对 Phase 1 的细化建议（贴合架构图）**

- **Sprint 1.1**：除追踪+表单+Contact/Company/Deal 外，可明确「**Integration Layer** 第一版」= 网站(HubSpot Form) + 关键行为(GA)；若有 LinkedIn/YouTube 需求，在本 Sprint 或 1.2 加入对应 Connector/埋点。
- **Sprint 1.2**：HubSpot 侧先做 **原子工作流**（Email / Content / Campaign 各一条最小可用的），再做了 MQL→Hot Leads 到 Salesforce（若有）的分配；**Lead Score** 在 Phase 1 用 HubSpot 内置规则即可，Phase 2 再由 Marketing Data Layer 算分回写。
- **Sprint 1.3**：**Nurture Orchestration** = 把已做的原子工作流按「培育路径」和「再激活路径」编排（信号可先为规则：如「表单提交→培育」「N 天未开→再激活」）；Dashboard 初版覆盖架构图中「Query 能回答」的流量、线索、管线、客户数。

按上述对应关系，团队的架构图可直接作为 Phase 0 需求讨论与 Phase 1/2 验收的**视觉基准**，Sprint 输出与架构图组件的对应关系也会更清晰。

### 2.2 阶段与 Sprint 总览

| 阶段 | 周期 | Sprint | 主要目标 | 核心输出 |
|------|------|--------|----------|----------|
| **Phase 0** | 2–4 周（含**跨团队协作等待**，如 Marketing campaign 侧 conversion strategy 1–2 周） | 0.1, 0.2 | 需求对齐、指标与数据实体、需求规格定稿；与 campaign 侧 conversion strategy 对齐 | 《营销数据指标体系 v1.0》《数据中台需求规格说明书》初稿；Phase 1 验收标准与排期；**campaign 侧 conversion strategy 对齐结论**（可选） |
| **Phase 1** | 4–6 周 | 1.1, 1.2, 1.3 | 追踪与数据模型、打分与 MQL、生命周期工作流与 Dashboard | 可用的 HubSpot 闭环、首版 Dashboard、Phase 2 需求细化清单 |
| **Phase 2** | 12–16 周 | 2.1–2.6 | 数据平台、ETL/Reverse ETL、统一看板与权限 | 统一营销数据中台、PQL/预测（可选）、看板与报表、验收文档 |

**Sprint 长度**：默认 **2 周**；可根据资源与优先级微调。

**排期原则**：每周安排**从简**，每 Sprint 内预留**宽松时间**（约 1–2 天/周用于沟通、返工、突发或缓冲），避免排满；若当周提前完成，可用于复盘或为下一 Sprint 做准备。  
**跨团队协作与等待时间**：若依赖其他团队产出（如 **Marketing campaign 侧**完成 campaign 的 conversion strategy），需在排期中**预留 1–2 周等待与对齐时间**，避免假设为「立即可得」；具体见 Phase 0 中与 campaign 侧的协作说明。

### 2.2.1 「Phase 2 需求细化」具体指什么

Phase 1 验收前后会做一次 **Phase 2 需求收集与细化**，目的是把「Phase 2 要建什么、先做哪块」写清楚，供 Phase 2 立项和 Sprint 2.1 技术选型用。具体包括：

| 做什么 | 说明 |
|--------|------|
| **收集问题与缺口** | Phase 1 运行中暴露的问题：例如埋点缺失或重复、口径不一致、报表看不到的维度、销售/CS 反馈「缺什么数据才能更好用」、与现有 CRM/ERP 的同步缺口等。 |
| **收集对 Phase 2 的期望** | 销售、CS、管理层希望 Phase 2 解决什么：例如要入仓的**数据源**（HubSpot、GA4、CRM、产品使用数据等）、要看板呈现的**指标与维度**（account health、product adoption、按区域/产品线拆解等）、是否要做 **PQL / 预测打分 / Reverse ETL**、是否有 i18n/多区域报表需求等。 |
| **谁提供输入** | 使用 HubSpot/报表的同事（市场、销售、CS）、产品/数据（若有埋点或产品数据）、IT（架构与现有技术栈）。 |
| **输出与用途** | 整理成 **《Phase 2 需求细化清单》**（可含优先级），作为 Phase 2 范围与 Sprint 2.1 **技术栈选型**的输入，避免 Phase 2 一上来就选型却不知道「要接哪些数据、要哪些看板」。 |

### 2.2.2 技术栈选型：何时做、选什么

Phase 1 **不涉及新选型**：HubSpot、GTM、GA4 等已按现有规划使用。  
Phase 2 的**技术栈选型**集中在 **Sprint 2.1**（Phase 1 验收完成、Phase 2 需求细化清单就绪之后），由相关技术团队共同评审。需要明确选型的范围大致如下：

| 选型项 | 可选方向（示例） | 说明 |
|--------|------------------|------|
| **数据平台 / 数仓** | Snowflake、BigQuery、Redshift、或现有企业数仓 | 存 HubSpot、GA4、CRM、产品使用等数据；需结合 IT 架构规范与现有技术栈。 |
| **ETL / 数据入仓** | 数仓自带 Connector、Airbyte、Fivetran、dbt（建模）或自建 | 把 MA/CRM/产品数据同步到数仓；与 9.4、2.2 指标与事件 schema 对齐。 |
| **Reverse ETL** | Census、Hightouch、或自建 API/脚本 | 把数仓里的得分、分层、PQL/预测结果写回 HubSpot/CRM；选型见 Sprint 2.3。 |
| **BI / 看板** | 数仓配套 BI、Tableau、Power BI、Looker、或自建 | 统一营销数据中台的报表与看板；需支持按角色权限。 |

**建议**：选型前先对齐《Phase 2 需求细化清单》和《Supcon Marketing Technology Recommendations》9.5 及 IT 架构规范，再评预算与资源；具体技术选型与排期以与相关技术团队的共同确认为准。

### 2.2.3 与敏捷开发方式的对应

本计划按**短周期、可交付、可调整**设计，与敏捷开发方式兼容。对应关系与建议如下。

| 敏捷要素 | 本计划中的体现 | 说明 |
|----------|----------------|------|
| **短迭代** | 2 周/Sprint，Phase 0/1/2 内多 Sprint 串联 | 与常见 Scrum 2 周迭代一致；可根据团队习惯微调周期。 |
| **可交付增量** | 每个 Phase 结束有可用的「可交付物」 | Phase 1：可用的 HubSpot 闭环 + 首版 Dashboard；Phase 2：统一中台 + 看板。避免长期只出文档不出可用系统。 |
| **反馈驱动** | Phase 1 验收 + Phase 2 需求细化；Sprint 内缓冲用于沟通与返工 | 先跑通 Phase 1，再根据真实使用反馈决定 Phase 2 范围与优先级，而不是一次性定死。 |
| ** backlog 与优先级** | Phase 2 需求细化清单（含优先级）、Phase 2 结束输出「迭代 backlog」 | 建议明确 **backlog 优先级由谁定**（如产品/GTM 负责人或跨职能评审），便于每 Sprint 从 backlog 中取高优先级项。 |
| **范围可调** | 排期原则已写「可根据资源与优先级微调」；Phase 2 可选 PQL/预测等 | 可根据反馈**缩减或后移** Phase 2 范围（如先不做 PQL、先做入仓+看板），不必一次做完。 |

**建议补充的敏捷实践**（按需采纳）：

- **Sprint 评审（Review）**：每个 Sprint 结束前，用约 1 小时演示本 Sprint 输出（如追踪是否生效、工作流是否跑通、Dashboard 是否可用），由使用方（市场/销售/CS）验收或提修改意见。
- **Sprint 回顾（Retrospective）**：每个 Sprint 结束前，用约 30–60 分钟做回顾（什么做得好、什么可改进、下个 Sprint 要试什么），输出简短改进项并纳入下个 Sprint 或 backlog。
- **每日/每周站会**：若有多角色协作，可设短站会（每日 15 分钟或每周 2 次）同步进度与阻塞，避免依赖卡在沟通上。
- **Definition of Done**：每个 Sprint 的「Sprint 输出」即该 Sprint 的 DoD；验收标准（如 Phase 1 验收标准）即 Phase 的 DoD，便于判断是否可进入下一阶段。

**结论**：在**短 Sprint、可交付增量、反馈驱动、范围可调**的前提下，本计划用于敏捷开发是**合理的**。Phase 0 以「最小必要对齐」为宜（避免过长），Phase 1/2 以「可用的系统 + 验收 + 需求细化」形成闭环，再根据反馈调整 Phase 2 范围与技术选型。

### 2.3 Sprint 执行明细（按周、从简 + 缓冲）

#### Phase 0：需求设计

| Sprint | 第 1 周（主项少、留缓冲） | 第 2 周（主项少、留缓冲） | Sprint 输出 |
|--------|---------------------------|---------------------------|-------------|
| **0.1**（2 周）<br>*实质：**Conversion strategy 设计*** | 与产品/数据/销售/CS 对齐：谁该找销售、何时、为何；漏斗各层要回答的问题。*缓冲：会议跟进、补充材料；**协作等待**：Marketing campaign 侧做 campaign conversion strategy（1–2 周），可并行启动，预留对齐时间* | 确定必选事件（表单、下载、Webinar、Demo）、Contact/Company/Deal 属性与枚举；**与 campaign 侧对齐**：将 campaign 的 conversion strategy（转化目标、Content/Campaign 维度、归因口径）并入事件与枚举。若有 CRM/ERP，对齐边界。*缓冲：初稿修订、**等待 campaign 侧产出（1–2 周）及对齐* | 《营销数据指标体系 v1.0》初稿；《数据实体与事件规范》初稿（对应 9.4）；Phase 1 范围与假设清单；**campaign 侧 conversion strategy 对齐结论**（可选） |
| **0.2**（2 周） | 定稿指标体系与数据实体；起草《数据中台需求规格说明书》初稿（为 Phase 2 准备）。*缓冲：评审与修改；若 campaign 侧产出延后，可在此周完成对齐* | 定义 Phase 1 验收标准（追踪覆盖、MQL 分配、至少 1 条培育流 + 1 条再激活流、Dashboard 初版）；排定 Phase 1 的 Sprint 1.1–1.3 时间表与负责人。*缓冲：Kickoff 准备* | 《营销数据指标体系 v1.0》定稿；《数据中台需求规格说明书》初稿；《Phase 1 验收标准与排期》；Phase 1 Kickoff 就绪 |

**Phase 0 执行说明（详细）**

**Sprint 0.1 的实质**：做 **conversion strategy（转化策略）设计**——定义「谁算 MQL、何时转销售、为何（归因）」以及支撑这些决策的漏斗问题、必选事件与数据实体；不执行具体触达，只把策略与数据基础定清楚，供 Phase 1 落地。

**与 Marketing campaign 侧的协作**：**Marketing campaign 同事**会负责**他们 campaign 侧的 conversion strategy**（如活动/内容/广告的转化目标、触点、口径），预计需要 **1–2 周**。团队需**预留等待与对齐时间**：在 Sprint 0.1 或 0.2 中安排与 campaign 侧对齐，将他们的 conversion strategy 与团队的《数据实体与事件规范》/指标体系合并或对齐（如必选事件中的 Content/Campaign 维度、归因口径）。排期时预留 **1–2 周**用于等待 campaign 侧产出及后续对齐，该时间可计入 Phase 0 总周期或 Sprint 0.1/0.2 的缓冲。

下面把 Phase 0 里每一件事具体解释成「要做什么、和谁做、产出什么」，方便按周执行。

**为何是「销售+CS」一场？**  
销售（Sales）和客户成功（CS）都用同一套数据（Contact、Company、Deal）和生命周期阶段：**销售**关心「谁该转成线索/商机、何时跟进、为何值得跟」；**CS** 关心「哪些客户该重点维护、谁有扩展/流失风险、为何」。两者对「谁、何时、为何」的共识会影响 MQL 转交、成单后归属、以及 Phase 1 的得分与工作流设计，所以放在一场里一起对齐，可以减少口径不一致，也少开一场会。  
若团队**没有独立 CS** 或 CS 不参与线索/商机定义，可只邀**销售**；若**销售与 CS 流程分离、关注点差异大**，也可拆成「销售一场、CS 一场」，按实际组织架构调整即可。

**建议邀请市场侧同事（Marketing）参与需求**  
市场同事是**渠道、内容、活动与培育**的直接负责人，他们能提供：**漏斗各层要回答的问题**（流量从哪来、哪些内容/活动带来留资、培育效果如何）、**必选事件**（表单、下载、Webinar、活动报名等）、**Content/Campaign 维度**（白皮书、博客、视频、Webinar、活动、广告）以及**归因与报表**需求。若不邀市场，需求容易偏「销售要什么线索」，而忽略**触达逻辑、培育路径和报表口径**。  
**建议**：Phase 0 对齐会至少有一场包含**市场**（可与销售+CS 合并为「市场+销售+CS」一场，或市场单独一场讲渠道/内容/活动需求）；Phase 2 需求细化时也请市场参与，提供对「要入仓的数据源、要看板呈现的指标与维度」的输入。若市场团队较大，可邀**内容、获客、活动/品牌**等负责人或代表。

**「需求侧+执行侧」指谁？如何安排？**  
- **需求侧**：负责「要什么功能、什么事件、什么指标」——产品+架构视角，定需求与口径；若无独立数据岗，也由需求侧定事件与指标口径。  
- **执行侧**：负责把「事件、表单、追踪」落到网站/前端——**网站开发**主责追踪与数据对接，**前端**主责表单与前端体验；执行侧需要知道：要埋哪些点、哪些表单、传给谁（如 HubSpot），以及谁做哪块。  

**团队对齐会建议**：  
- **第一场「市场+销售+CS」**：需求侧 + 市场/销售/CS 同事，对齐「谁该找销售、何时、为何」和漏斗要回答的问题；需求侧负责收需求、记结论，不负责执行细节。  
- **第二场「需求侧+执行侧」**：需求侧 + 网站开发 + 前端。需求侧讲清：要哪些必选事件、Contact/Company/Deal 属性与枚举、追踪与表单的**范围与验收标准**；网站开发、前端确认**能实现什么、谁做埋点、谁做表单、谁对接 HubSpot**，把执行分工谈清楚。这样**埋点、表单、联调**由执行侧承担，需求侧专注需求、口径、验收和 Phase 1/2 节奏。  
- 若暂无独立「市场/销售/CS」同事（如创业早期），第一场可简化为需求侧 + 任何能代表「线索/商机定义」的人，或需求侧基于已有文档先定一版，再找机会补对齐。

**如何平衡「执行侧有归属感、需求侧不过载」**  
- **给执行侧（网站开发、前端）有归属感和变化的工作**：  
  - **模块归属**：例如网站开发主责「追踪与数据对接」（GTM/HubSpot 追踪、事件上报、与后端或 HubSpot API 的对接），前端主责「表单与前端体验」（HubSpot 表单嵌入、落地页、前端交互与校验）；两人可轮换或交叉支持，但各有主战场，避免都只做「按清单埋点」的重复劳动。  
  - **参与「怎么实现」**：第二场对齐会里留时间让执行侧提「用 GTM 还是直接写、用现成组件还是自建、怎么少重复」等方案，需求侧只定范围和验收标准，具体实现由执行侧选，既有所有权又不只是执行任务清单。  
  - **适当自动化/工具化**：鼓励执行侧用 GTM 模板、脚本或简单工具把重复埋点/表单配置沉淀成可复用流程，减少重复劳动，也有「优化流程」的空间。  
- **把需求侧的工作框在「定规则、验收、解阻塞」**：  
  - **用 Phase 0 产出当「合同」**：《营销数据指标体系》《数据实体与事件规范》《Phase 1 验收标准》写清楚「要什么、验收什么」，后续需求侧只按文档评审和验收，不反复口述或亲自改每一处细节。  
  - **只做「要什么」和「通过没」**：需求侧不亲自做埋点/表单/联调；若某块必须需求侧兜底（如 HubSpot 工作流、打分规则），尽量做成「一次定规则、后续可复用」，或交给执行侧按规则在 HubSpot 里配置，需求侧只做最终检查。  
  - **阻塞才介入**：日常执行交给执行侧，需求侧只在**口径冲突、依赖缺失、验收不通过**时介入拍板或协调，避免需求侧时间被琐碎执行占满。

### 基于首次会议纪要：接下来两周 Sprint 执行建议

以下根据**首次会议纪要**（工作时间安排、数据处理、官网开发、客户分类与工具、后续规划）与本指南 Phase 0.1 对齐，给出**接下来两周**可直接执行的任务与产出；会议结论已纳入，便于真绮、梁雨晴、需求侧按角色分工。

**会议关键结论摘要**  
- **Sprint 周期**：下一阶段 = **两周**（与指南一致）。  
- **HubSpot**：先用**免费版**，需求明确后再联系销售；真绮从开发角度查 **HubSpot API**（官网连接、Email）；梁雨晴查看 HubSpot 产品（收集、marketing dashboard、business card 等）。  
- **数据层**：前期数据可放在 **Hive**，做仪表盘时再单独拎出；**数据层不外包**，需先想好结构；梁雨晴向肯特了解 **Hive / Postgre 收费**。  
- **Salesforce**：**不对接完整数据**，只把优质线索推给对方，对方在系统里加「来自 SMB marketing」的 category，降低对接成本、专注可控方向；需对方**反馈**完善响应逻辑，数据量少时人工调整。  
- **Dashboard**：整合**整个营销数据**，**Google Analytics 数据放入 dashboard**，供后续 AI 使用；**MA 的 data layer 有必要**。  
- **官网**：**官网维护可外包**，数据层与结构己方设计；真绮以**项目经理**角色写需求、明确双方负责部分；前端可考虑 **Framer / Webflow** 等 design tool；内容可向开发团队要；真绮帮忙问**日本官网**（supcon.co.jp）情况。  
- **客户分类**：HubSpot 内用 **customer 数据结构 + 多标签**，按标签 **bucket 分类**，决定业务逻辑；收集 name、industry、职位、公司规模、感兴趣产品等，**不同分类推送不同内容**。  
- **小工具**：名片录入+AI 分类工具计划在**汉诺威展会前**完成；企业微信共享表可做成类小程序，拍名片→表单→自动化分类。  
- **资源**：Email 对接需**市场部邮箱及 key**（非密码），由凯森协调、IT 开新账号；真绮问日本官网；梁雨晴建议先出**日程计划（calendar plan）**；真绮**测试不同技术并给出建议**。

## 5. 核心能力实施要点

### 5.1 「谁该找销售、何时、为何」—— 线索与商机识别（含 PQL）

- **PQL 与 MQL 的区分**
  - **PQL（Product Qualified Lead）**：基于产品使用的购买信号，如 team expansion、feature adoption、engagement。需有产品使用数据后才能在系统中落地。
  - **MQL（Marketing Qualified Lead）**：基于营销行为（内容下载、Webinar、Demo 请求）+ 属性（行业、规模、地区）。Phase 1 以 MQL 为主。
- **Phase 1（规则驱动）**
  - **谁**：用 9.4 的 Contact 属性（company, industry, region, product_line, product_category）+ 行为（内容下载、Webinar、Demo 请求）界定 MQL/SQL。
  - **何时**：用 HubSpot lead score 阈值 + lifecycle_stage 变更触发「创建/分配商机」或「通知销售」工作流。
  - **为何**：在 Contact/Deal 上记录 lead_source、lead_source_detail、conversion_event（见 9.4.2、9.4.3），报表中按来源/内容/活动做归因。
- **Phase 2（可扩展 PQL + 预测）**
  - 有产品使用数据后：用 team expansion、feature adoption、engagement 等定义 PQL，并写入 HubSpot/CRM（经数据平台 + Reverse ETL）。
  - 在统一数据平台复用同一套维度与事件，增加「转化概率」「高价值账户」等预测字段；再通过 Reverse ETL 或 API 写回 HubSpot/CRM，驱动优先级与路由。

### 5.2 产品/行为数据 → HubSpot（数据管道）

- **Phase 1**
  - 网站/落地页：GTM + HubSpot 追踪代码 + 标准事件（9.4.3）→ HubSpot 自动识别/更新 Contact。
  - 表单与转化：HubSpot Forms + 工作流，保证 Demo/下载/Webinar 等进入统一 Contact 与 Deal 模型。
  - 与内部 CRM/ERP：若有线下或既有系统，用 n8n（或 Zapier、Make、Tray.io 等）做定时/触发同步与 API 工作流，保持 Contact/Company 主数据一致（见报告 4.1、5.2）。
- **Phase 2**
  - 统一数据平台：HubSpot、GA4、CRM、产品使用数据等 → 经 ETL 入仓（报告 9.2、9.5 Phase 2）。
  - 产品数据入 GTM：产品使用数据入仓后，经 Reverse ETL（Census、Hightouch 或自建）写回 HubSpot/Salesforce，使销售与 CS 在 CRM/报表中看到 real-time engagement、usage trends、expansion signals。
  - Reverse ETL 同时承载「得分、分层、预测结果」从数据平台写回 GTM 系统（报告 9.2 数据流）。

### 5.3 线索打分（规则 → 可选 AI/ML）

- **Phase 1**：使用 HubSpot 内置打分——行为分（页面、邮件、表单、活动）+ 属性分（firmographics：行业、公司规模、地区；产品兴趣）。与 9.4 的 product_line/product_category、lifecycle_stage 一致，便于报表和路由。
- **Phase 2**：在数据平台用 product behavior、firmographics、engagement patterns 训练 ML 模型（如 MQL 转化概率、商机赢单概率）；结果写回 CRM/MA。预测模型需生产化（部署、监控、定期重训）；可由数据/算法团队负责，GTM 侧定义指标与用数场景。

### 5.4 仪表盘与报表（销售/CS/管理层可见）

- **Phase 1**：HubSpot Dashboard 按漏斗层（Attract/Inform/Convert/Engage）建报表——流量与来源、线索与 MQL、管线与转化率、客户数（见 9.5 Phase 1）。确保核心指标与 9.4、2.2 的指标体系一致，便于 Phase 2 复现。
- **Phase 2**：统一营销数据中台——同一套指标与维度，覆盖全渠道、全触点、资源流转与归因（见 9.2、9.5 Phase 2）。面向销售/CS/管理层的可见内容：account health、product adoption、expansion opportunities、churn risk；在数据与产品打通后由看板与报表呈现。按销售/CS/管理层划分权限（报告 9.5 Phase 2 权限模块）。

### 5.5 与产品/数据团队的协作（埋点、口径、质量）

- **Phase 0**：一起敲定：哪些事件必选（9.4.3）、属性命名与枚举（9.4）、核心指标定义（2.2），输出《营销数据指标体系 v1.0》与《数据中台需求规格说明书》初稿。
- **Phase 1**：验证埋点与口径：从 GTM/HubSpot 到报表的链路是否一致、是否有缺失或重复；将问题与需求写进 Phase 2 需求规格。
- **Phase 2**：数据平台与产品埋点/数据团队对齐：事件 schema、身份解析（contact_id/account_id）、增量与全量同步方式。

### 5.6 生命周期营销与关键转化节点

- **用户旅程**：首触（首次访问/留资）→ onboarding 完成（首份内容/首场 Webinar）→ first meaningful creation（首次深度参与）→ MQL → SQL → 成单；高价值用户状态对应持续高互动线索或已购客户中的高使用/扩展意向，可作为 Engage 层优化目标。
- **渠道**：以 Email + 落地页/内容为主；若后续有 in-app、push，可与 Email 纳入同一套 Contact 与事件模型，在 Phase 2 统一触达与归因。
- **自动化流（HubSpot 工作流）**：欢迎/入门序列；培育序列（按 persona：industry、product_line、region）；再激活（基于最后活动时间/未打开天数）；与品牌、产品、CX 对齐；关键节点（如 Demo 请求、高得分）可转为销售人工跟进。
- **关键转化点优化与 time-to-value**：为每一层建漏斗报表，识别卡点；通过优化入门流程、培育内容、再激活提高各层转化率；用 A/B 测试验证文案、时机、流程。
- **A/B 测试与数据驱动**：Phase 1 在 HubSpot 内做邮件/落地页 A/B 测试（主题、文案、CTA、发送时间），关注统计显著性；设计规范实验（假设、对照组、样本量、统计检验）。Phase 2 在数据平台统一 A/B 实验与用户行为数据，做多触点归因与实验效果分析。用分析工具与看板指导策略。
- **多区域/国际适配**：Phase 1 用 region、语言或国家属性做列表与工作流分支；不同区域使用不同邮件模板、发送窗口（时区）。Phase 2 若有 i18n/l10n 需求，可在内容与邮件中接入多语言与区域化配置；报表按 region 拆解转化与留存。
- **与市场、产品、客户体验的协作**：生命周期战役与市场品牌一致；功能发布时与产品协作，将新功能/用例融入邮件或落地页；用户反馈（NPS、支持工单、访谈）纳入培育与再激活内容；与 CX 一起设计挽回或再教育路径。
- **文案与写作**：邮件与落地页需简洁、有说服力、有行动导向、符合品牌；可在 Phase 0 约定文案原则与审批流程。

### 5.7 产品营销——定位、叙事与发布 GTM

- **定位与叙事**：负责产品组合的 positioning and messaging，将复杂能力转化为清晰、差异化的价值主张；面向技术与非技术受众；白皮书、案例、Webinar、落地页与销售话术保持一致叙事；与 9.4 的 content 维度与 UTM/归因衔接。
- **发布 GTM 与跨职能协同**：从 kickoff 到 post-launch optimization，协调产品、销售、市场；时间表、里程碑、内容与触达节奏与 Phase 1/2 的 HubSpot 活动、工作流、报表对齐；与产品、研发、解决方案定期对齐，把竞品动态、客户反馈、分析师观点纳入需求与发布节奏。
- **销售赋能**：竞品情报（定位、功能对比、赢单/输单话术）；Demo 脚本与差异化亮点；ROI 框架；对外代表产品愿景与差异化（客户、分析师、行业活动）。
- **内容与叙事线**：从技术博客、发布公告到高管/决策层叙事；整合营销项目支撑 self-serve 与 sales-led 双轨；与漏斗及生命周期触达一致。
- **市场研究与品类领导**：理解技术/行业如何改变客户工作流；跟踪竞品动态；识别品类领导机会；定义产品/功能采用类指标；用实验与数据优化定位与话术；与仪表盘与 A/B 衔接。

## 6. 可选增强（Phase 2 及以后）

- **AI 驱动的账户/客户研究（如 LLM 摘要）**：根据公司官网、新闻、融资、技术栈等，自动生成「为何适合联系、可谈什么」的要点，供销售/CS 使用。前置条件：数据与权限就绪、API 与工作流可调用 LLM。可与「为何找销售」结合，在 CRM/MA 中展示推荐联系原因或谈话要点字段。
- **数据仓库与 dbt（若采用）**：若 Phase 2 采用数仓（如 Snowflake、BigQuery、Redshift），用 dbt 做指标与维度建模，保证与 9.4、2.2 的定义一致；输出层支撑 Reverse ETL（Census/Hightouch）与 BI/Dashboard。ETL/Reverse ETL 与数据平台建设通常需要 Python、SQL 及 API 集成能力。
- **从 PLG 向 Enterprise 延伸（若适用）**：Phase 2 数据平台、PQL 设计、Reverse ETL 可支撑产品使用信号（team expansion、feature adoption）入仓并写回 CRM，使销售/CS 可见「哪些账户该联系、为何、谈什么」。

## 8. 小结

- 本指南将 GTM Martech 职责（识别高意向账户、数据管道、打分、仪表盘、与产品/数据协作）、**生命周期营销**（培育、再激活、多区域、A/B）与**产品营销**（定位与叙事、发布 GTM、销售赋能）落到 Supcon 已有的 Phase 0/1/2 和漏斗/数据模型上。
- **Phase 0**：需求对齐与需求规格定稿，输出指标体系、数据实体与事件规范、Phase 1 验收标准与排期。
- **Phase 1**：优先开箱即用（HubSpot + GTM + 标准数据实体）完成「谁该找销售、何时、为何」的验证闭环，并输出可复用的指标体系与 Phase 2 需求规格。
- **Phase 2**：按需自建统一数据平台、Reverse ETL、ML 模型、AI 账户研究（可选），在统一数据平台上实现全链路数据、可选预测打分与 Reverse ETL，随反馈迭代；技术选型需在 Phase 1 验证完成后，结合 IT 架构规范与资源评估，由相关技术团队共同确定。
- 具体技术选型与排期仍以《Supcon Marketing Technology Recommendations》9.5 及与相关技术团队的共同确认为准。
